## Decision: keep, don't sunset.
The typed envelope (#53) added `{ owner_text, attachments, images, model }`. The door still accepts the legacy `{ input: string }` shape and maps it to `owner_text` (chat-serve.ts). This issue records the bounded contract so it's tracked, not assumed.

## The legacy contract (why it's safe to keep)
- **owner_text only.** Legacy `{input}` maps to `owner_text` and carries NO attachments channel — so it can drive grammar / lockdown / voice exactly like owner-typed text, and cannot introduce attachment content into any channel.
- **Loopback + Origin-gated.** The door binds `127.0.0.1` and rejects cross-origin POSTs (browsers always attach Origin; only trusted local actors reach it). Pasted `<<<...>>>` in legacy input arrives as inert plain text — no spoof reopening (the nonce + content neutralization apply to attachment framing, which legacy input never triggers).
- **No structural distinguisher** between legacy owner text and a real frame — safety rests on source-trust (loopback + Origin), not shape. That's acceptable for a local, owner-only door.
