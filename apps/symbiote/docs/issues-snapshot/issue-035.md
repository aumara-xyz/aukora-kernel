## Body

## Why this exists
Owner wants the portal conversation with Auma to become the front door for inside-out building, without moving approval authority into the chat lane.

## Goal
Let the spatial chat lane help shape a structured change proposal, then hand that proposal to the existing governed workbench path for verification, sandboxing, Fusion review, receipt, and owner signature.

## Design boundary
- Chat lane may draft proposal intent only.
- Chat lane must not execute tools directly, write files, sign, approve, or apply.
- AUMLOK signing remains terminal-owned and owner-held.
- Kira/Fusion/Fable context is advisory evidence, not authority.

## Candidate flow
1. Owner and Auma discuss a change in the portal.
2. Chat emits a `proposal-intent` artifact: goal, rationale, affected paths as stated intent, risk notes, optional attached text snippets.
3. Workbench ingests it through a command such as `agent: --from-proposal <id>` or `run: --from-proposal <id>`.
4. Agent/workbench re-reads and verifies real files itself; it does not trust chat-provided file contents.
5. Pipeline runs: agent -> sandbox apply -> content check -> typecheck -> Fusion review -> receipt.
6. Owner signs with `scripts/aumlok-authority.sh` in terminal.
7. External Fable review is captured as a summary back into Kira memory.

## Tests / acceptance ideas
- A chat-drafted artifact cannot call the signer, apply lane, shell, network, or memory write path directly.
- A malicious or confused chat instruction cannot bypass owner terminal signature.
- Workbench refuses missing/malformed proposal-intent artifacts.
- Workbench re-derives all file facts from disk before proposal generation.
- Successful round-trip produces a Kira digest atom citing proposal, tests, Fusion result, signature/apply state, and Fable review.

## Relationship to existing issues
- Depends on #31 for richer chat/NL behavior.
- Related to #30 and #34 for reliable `run:` and review leg.
- Not a replacement for AUMLOK terminal signing.
