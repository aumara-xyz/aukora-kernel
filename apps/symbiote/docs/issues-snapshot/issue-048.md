## The discrepancy
- scripts/status.sh:17 prints: `AUMLOK: unlocked (sha256 dev-shim — NOT cryptographic yet)` when the unlocked branch is hit.
- authority/aumlok/ceremony.ts:170-185 shows the real current flow: on a correct unlock phrase, it writes the session file, then (24Z.77) mints a daemon-co-signed unlock EPOCH authorized via a real Ed25519 signature — not a "dev-shim." The comment at ceremony.ts explicitly notes memory writes are authorized off the *signed epoch*, not the UID-writable session boolean, specifically because the plain session boolean is forgeable and the Ed25519 epoch isn't.

status.sh's wording predates that epoch-signing work landing and now describes a weaker security model than what's actually implemented. Not a functional bug (AUMLOK's real gate is unaffected) — but `status.sh` is the tool used repeatedly this session to sanity-check AUMLOK state, and it's currently underselling what's real.

## Proposed fix
Update status.sh:17's unlocked-branch message to reflect the real Ed25519 epoch-signed flow (and probably split "session file present" from "epoch signed" into two separate checks, since they're materially different guarantees — a forged session file with no epoch should read differently than a fully signed unlock).
