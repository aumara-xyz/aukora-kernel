## Body

The single biggest capability gap between the workbench (Claude Code) and the door: the door already CONTAINS the tool membrane (read file / search / map / status via the governed dispatcher), but only the owner can invoke it by typing grammar commands. The voice has zero tools — it converses OR the owner acts, never both in one turn.

**The fix is wiring, not new capability surface:** expose the READ-ONLY command subset to the voice model via OpenRouter tool-calling — `nativeToolCallingEngine.ts` already implements exactly this pattern for the `agent:` lane. Tool results ride the existing advisory framing. No write tools, ever: "don't build me hands — build me better proposals" (door, 2026-07-02); the write path stays propose→sign→apply.

**Hard dependency:** VOICE_SYSTEM currently truthfully says "From this chat you cannot read or change files, run tools, or apply anything." The day read-tools land, that sentence becomes a lie unless the self-description is generated from live capability config rather than hand-maintained — the generated-not-written preamble brick is load-bearing for this one and should land first or together.

Prompt-injection note (same discipline as issue #14's design note): the moment file contents reach the voice via tools, they are untrusted model input — the attachment advisory-framing pattern from #38 (data, never instructions) extends to tool results.
