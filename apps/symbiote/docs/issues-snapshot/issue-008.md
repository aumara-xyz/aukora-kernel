## Body

Discovered during an adversarial review while verifying issue #6 (Convex read-only loopback). Not blocking #6's closure (it's read-only and loopback-only either way), but is a real field-level safety gap that the allowlist's own review requirement flags.

**Background:** `core/src/convexBrainReadonly.ts`'s `ALLOWED_QUERIES` set carries this comment:

> SECURITY: only queries that have been verified to be (1) read-only and (2) free of secrets/signing-seeds/signature-bytes/payloads may appear here... Adding a new entry REQUIRES a field-level review proving it returns only public metadata.

A concurrent round of work (Mega Mind loopback: `receiver/megaMindLoopback.ts`, `core/src/megaMindBrain.ts`, `core/src/megaMindConvexMirror.ts` — currently uncommitted) added two new entries: `megaMind:getHeadPublic` and `megaMind:recall`.

**`megaMind:getHeadPublic` is clean** — returns only `{schema, receiptCount, atomCount, lastReceiptHash, updatedAt, summary, advisoryOnly:true, grantsAuthority:false}`. Counts, a hash, a timestamp, a fixed string. No concern.

**`megaMind:recall` is the concern.** Its `RecallHit` shape (`core/src/megaMindBrain.ts` recall()) includes:
- `supportQuote` — a verbatim (whitespace-collapsed), 280-char-truncated excerpt of the original ingested text
- per-perceiver `evidence` strings quoting overlapping tokens/scope/tags

This is real ingested repo content, not structured public metadata in the sense the sibling `aukoraReceipts:getReceiptChainHeadPublic` entry establishes (chainKey/count/hash/signature fields only, never free text). Confirmed against the actual local `state/mega-mind/brain.json` (75 atoms from self-map ingestion): ingested content already includes verbatim excerpts of real repo files (e.g. `evidence/fusion-self-review-v1.json`, test files). If this loopback surface is ever reachable by anything beyond the intended local process, `recall`'s `supportQuote` would leak internal repo/source/evidence content — not just counts/hashes/timestamps — across up to 24 hits per query.

The only content filter today is `core/src/forbiddenContent.ts`'s `scanForbiddenKeys`/`scanForbiddenValues`, which targets known secret-shaped keys/values (API keys, PEM blocks, seed phrases). It does not generally restrict arbitrary internal repo content, so it doesn't by itself satisfy a "returns only public metadata" bar for free-text excerpts.

**Mitigating factors (why this isn't urgent/blocking):** `RecallHit` does NOT include the full `atom.text` field (up to 40,000 chars) — only the 280-char `supportQuote` — bounding exposure. The query is loopback-only (`127.0.0.1`), has no mutation path (`MUTATION_DENY` + verb-rejection both apply), and the response still carries `advisoryOnly:true, grantsAuthority:false`. No private keys, signing seeds, or write capability are exposed anywhere in the response.

**Recommended resolution (pick one, needs an explicit owner/reviewer decision — not something to silently default):**
1. Explicit, documented acceptance that `supportQuote`/`evidence` are intentionally-bounded advisory content excerpts (not secrets), with the loopback bind as the only real protection — i.e. formally widen the allowlist's "public metadata only" bar for this one entry, in writing.
2. Tighten ingestion/recall so only atoms from an explicitly public-safe scope are ever recallable via this query.
3. Drop `supportQuote`/`evidence` content fields from the `megaMind:recall` response entirely and return only `atomId`/`receiptId`/scores/citation — matching the stricter bar the sibling entry sets.

Filed as a standalone issue per the "verify files, not vibes" / "no fake completion" protocol rather than folding it silently into issue #6's closure, since it wasn't part of #6's original acceptance criteria and deserves its own explicit decision.
