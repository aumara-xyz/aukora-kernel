## Body

Captured from third-party static architecture/red-team review of the latest GitHub snapshot. Verify against current code before implementation.

Concern:
core/src/nativeLiveApply.ts may touch real repo bytes before the whole operation is complete. If validation, git add/commit, ledger finalization, or receipt writing fails, callers may see a refusal-shaped result even though live state changed.

Target invariant:
A result may only claim no-effect/refused if a byte-for-byte pre/post check proves repo content and index did not change. Any real commit or partial live mutation must be represented by a distinct explicit outcome.

Desired outcome model:
- refused_no_effect
- apply_failed_restored
- committed_receipted
- committed_unreceipted_quarantine
- reverted_after_failure

Required hardening:
- preflight/snapshot before live writes
- no mkdir/write during pure validation
- restore worktree/index on write/git failure
- quarantine state if commit succeeds but receipt/ledger fails
- tests that intentionally fail after partial write/git-add/git-commit/ledger points and prove the state/outcome is honest

Non-goal:
Do not widen live authority. This is transactionality and honest outcome semantics for the existing signed apply lane.
