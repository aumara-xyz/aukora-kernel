## Body

## Problem

Skunkworks / audit-node sandbox chain confirmed a defense-in-depth break: with one valid owner signature, a proposal that targets the live-apply gate source can rewrite the gate itself. On the next invocation, the modified gate can accept forged/unsigned applies. This is not an unsigned remote exploit — it requires a valid owner signature first — but it defeats the expectation that the gate cannot be rewritten by the lane it protects.

## Evidence summary

Reported in `docs/INBOX.md` as: `HIGH: one-signature gate self-unlock confirmed end-to-end`.

Sandbox-only chain on freshest tested HEAD `c8d1200`:
- throwaway ed25519 key only; real AUMLOK key/live tree/brain never touched
- a validly signed proposal rewrote `core/src/nativeLiveApply.ts` to neuter `validateAllFilesOrRefuse`, hash/signature/replay checks
- the apply succeeded because the current live gate classifier sees `write core/src/nativeLiveApply.ts` as `write_gated`, not `sacred`
- on the next invocation, a forged/unsigned proposal applied through the neutered gate

Root cause:
- ratified `docs/policy-rings/ring-table.json` marks gate machinery as Ring 0, but the live apply path does not consume PolicyKernel yet
- current hardcoded keyword sacred-net / `kernelActionClassifier` does not fence the gate implementation that enforces the fence
- `authority/gate/.gate-integrity.sha256` does not cover `core/src/nativeLiveApply.ts`

## Acceptance direction

Before routine PolicyKernel wiring, add a small self-protecting stopgap at the live-apply chokepoint:

1. Hardcoded self-referential Ring-0 deny-list inside `core/src/nativeLiveApply.ts` itself, checked before signature/apply logic, refusing payloads targeting at minimum:
   - `core/src/nativeLiveApply.ts`
   - `core/src/kernelActionClassifier.ts`
   - `core/src/appliedProposalLedger.ts`
   - `core/src/policyKernel.ts`
   - `core/src/proposalHash.ts`
   - `core/src/aumlokAuthorityRoot.ts`
   - `authority/gate/**`
   - `docs/policy-rings/**`
2. Extend `authority/gate/.gate-integrity.sha256` or equivalent runtime byte-pin to cover live-apply gate machinery, including `nativeLiveApply.ts`.
3. Owner-facing proposal/evidence must loudly surface Ring-0/gate-machinery targets before signing.
4. Later #78 Step 2 still wires `policyKernel.decide()` into live apply and refuses Ring-0 / `allowed:false` regardless of signature; this issue is the pre-wiring stopgap so the wiring gap cannot be exploited.

## Non-goals

- Do not weaken AUMLOK.
- Do not add broad auto-apply/session grants.
- Do not rely on model manners or Fusion consensus for this; it must be mechanical.
