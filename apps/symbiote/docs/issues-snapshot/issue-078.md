## Body

Captured from third-party static architecture/red-team review of the latest GitHub snapshot. Verify against current code before implementation.

Concern:
Self-modification is too broad unless code is classified by effect class and ring. Editing UI/docs is not the same as editing the gate, signer, test runner, live apply, or policy classifier. Policy logic also appears spread across multiple modules and servers.

Goal:
Define rings and centralize policy decisions in one PolicyKernel used by workbench, sandbox, live apply, dashboard/spatial command surfaces, and future read-tools.

Rings sketch:
- Ring -1: human physical authority, hardware keys, recovery
- Ring 0: sacred authority: AUMLOK root, signer/verifier, gate laws, kill switch, scanners, identity/private boundaries
- Ring 1: governance substrate: live apply, sandbox runner, policy classifiers, test gate, receipt validators, update mechanism, Convex mutation gateway
- Ring 2: organism runtime: Kira, workbench loop, native agent, Fusion review, dashboard commands
- Ring 3: body/UI/docs
- Ring 4: labs/deferred/experiments

Policy rules sketch:
- Ring 3/4 can be ordinary owner-signed after sandbox/test.
- Ring 2 requires stronger targeted tests + advisory review.
- Ring 1 requires full suite, baseline trusted runner, explicit Ring 1 owner signature, possibly second reviewer/key.
- Ring 0 almost never, with cooling period/manual out-of-band ceremony.
- Ring -1 never by organism.

Acceptance:
- one PolicyDecision schema with effectClass, ring, allowed, requiredCapabilities, reasons, policyHash
- all proposal/live apply paths consume the same policy decision
- tests prove proposals touching Ring 0/1 cannot pass through ordinary UI/docs path
- policyHash included in future PromotionBundle.
