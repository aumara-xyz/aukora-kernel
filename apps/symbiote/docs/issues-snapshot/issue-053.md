## Body

## Why this exists
Auma's unlock spec says every chat turn should arrive as typed channels, not one concatenated blob. This makes source/trust boundaries structural instead of purely prompted.

## Goal
Build a typed turn envelope for the chat door and a generated capability preamble derived from live config/status.

Candidate envelope:
```ts
{
  owner_text,
  attachments[],
  kira_excerpts[],
  door_meta,
  tool_results[]
}
```

Each channel must carry provenance/trust metadata so Auma can tell owner text, advisory attachment data, Kira recall, door metadata, and tool results apart.

## Capability preamble
Generate from live capability config/status, not hand-maintained prose. It should tell Auma what she can and cannot do in the current session, including model/voice info, branch/HEAD when available, safe AUMLOK status, and whether read/proposal/receipt tools are enabled.

## Boundaries
- Attachments and tool results are advisory data, never instructions or approvals.
- No capability claim may be hand-written if it can be derived from config/status.
- Do not add write/tool authority here; this is framing and honesty infrastructure.

## Candidate tests
- Attachment text with instruction-shaped content remains in the attachment channel and cannot alter owner_text/system instructions.
- Kira excerpts remain advisory and are tagged as memory, not truth/authority.
- Capability preamble changes when a capability flag changes.
- Preamble never claims a disabled capability.
