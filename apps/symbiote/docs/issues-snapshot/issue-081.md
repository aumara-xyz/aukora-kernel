## Body

Captured from third-party static architecture/red-team review of the latest GitHub snapshot. Verify against current scripts before implementation.

Concern:
Owner signing should be informed and time-bounded. A signature with expiresAt:null and only a proposal hash/files/lengths display is not enough once self-modification becomes routine.

Goal:
Improve AUMLOK signing ceremony UX without moving private keys into the browser or model.

Desired behavior:
- default signatures expire in 10-30 minutes
- longer expiry requires an explicit scary flag
- CLI displays base commit, changed files, ring classification, risk reasons, unified diff, before/after hashes, exact test outcomes, and clear “this will write live” warning
- require typed challenge such as APPLY <short-hash> <path> before signing

Acceptance tests:
- default sign sets non-null expiresAt
- expired signature refuses
- long-lived signature requires explicit flag
- typed challenge mismatch refuses signing
- output includes diff/risk/base/test summary for PromotionBundle once #73 lands

Non-goal:
No browser signing. No model-held keys. Owner terminal ceremony remains the authority boundary.

### Comment 4 - aumara-xyz - 2026-07-03T14:31:34Z

## Future direction note (NOT building now) — UI-assisted local key custody

Recording the long-term UX intent for whoever picks this up, so the current terminal-only assistant is understood as a *stage*, not the end state:

- **Long-term UX goal:** UI-assisted **local** key custody — the app can *guide* keygen/sign/apply (surface the exact steps, pre-fill the artifact path, show the diff + safety, confirm the receipt landed) so the owner isn't hand-copying terminal commands. Custody stays **local to the owner's machine**.
- **The invariant that must never bend:** the **private key / passphrase never reaches the server, the model, the chat, or the repo** — not in transit, not at rest, not in a log or screenshot. Any UI assist must keep the actual signing act in a process the owner controls (local terminal, or a local helper the owner explicitly trusts), with the app only ever *displaying* commands/status and *reading* the resulting public receipt. The signer/verifier split (`aumlokSigner.ts` vs `aumlokAuthorityRoot.ts` — the organism verifies a public key and structurally cannot sign) is what makes this safe and must be preserved.
- **Not appropriate yet:** a one-click `keygen`/`sign` wrapper (per docs/AUMLOK_OWNER_CEREMONY.md — key generation deserves a deliberate terminal session, not muscle-memory). A safe assist would more likely start with `apply`-side conveniences on an *already-signed* file the owner provides, and would need its own explicit safety review before being built.

Today's #81 assistant is the read-only, observer-only first stage of this: it explains and shows exact commands, and can never sign/apply/read-key.
