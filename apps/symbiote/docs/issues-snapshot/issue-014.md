## Body

Source: owner-provided `imported tech (github etc)/hermes-agent-main.zip`. Inspected before any commitment: this is the REAL, actively-maintained, MIT-licensed "Hermes Agent" by Nous Research (https://github.com/NousResearch/hermes-agent) — a self-improving agent with a learning loop, cron scheduling, subagent delegation, six deployment backends (local/Docker/SSH/Singularity/Modal/Daytona), multi-platform messaging (Telegram/Discord/Slack/WhatsApp/Signal), LSP integration, its own CLI/TUI/web app. Real scale: 6,794 files, ~129MB uncompressed, Python + `uv` package manager — roughly 3x the size of Symbiote's entire current codebase.

**Owner's stated long-term goal:** "Aukora becomes its own IDE, and then that basically takes over all the functionality in Hermes in one controlled organism."

**Why this is NOT a port (explicitly rejected as an approach):** vendoring or rewriting 129MB of actively-maintained Python into Symbiote's TypeScript kernel would be slow, would immediately go stale against upstream Hermes development, and would be exactly the kind of large, hard-to-verify, "trust me it's done" change this project has been explicitly avoiding all session.

**The actual viable path — proven pattern, not theory:** the same approach already source-drafted in aukora-kira for the real upstream OpenCode agent (see issue #13) — Hermes stays Hermes, runs as a real external agent process. EVERY tool call it attempts gets routed through Aukora's own `authority/gate` risk classifier before any side effect executes. Nothing it does reaches the live repo without going through the existing sandbox-test → Fusion-review → AUMLOK-signed-apply pipeline that already exists and is already tested. Symbiote is the sovereign layer; Hermes is the powerful engine wrapped inside it.

**Phased scope (separate issues/commits per phase, per this repo's standing protocol — do NOT attempt this as one commit):**
1. **Understand Hermes's actual tool-call surface**: what does Hermes call when it reads/writes files, runs shell commands, etc.? (Likely `agent/` + `tools/` directories — needs a real read, not assumed from the README.)
2. **Design the gate boundary**: adapt the `opencodeAskBridge.ts` pattern from issue #13 for Hermes's specific tool-call shape (Python, not TypeScript — likely means a small Python-side shim calling into, or being checked by, Aukora's gate logic via a well-defined boundary, e.g. a local RPC/subprocess call rather than an in-process import).
3. **Prove the gate on the smallest possible surface first**: ONE Hermes tool call, gated, demoed live — same "smallest verifiable slice" discipline as everything else this session. Do not wire the whole tool surface at once.
4. **Expand incrementally**, each phase demoed and verified before the next.

**Explicitly not started yet.** This issue exists to make sure the initiative and its scale are on record, not lost, and not attempted as a single invisible rebuild. Owner sign-off needed on each phase before implementation.
