## Scope
Track the future architecture brick Guardian called **backend-agnostic governed persistence**.

This is planned, not shipped. It is not a new authority path.

## Goal
Define a pluggable persistence adapter interface so the receipt chain / evidence store can run on different hosting backends with identical authority and verification semantics.

Candidate backends:
- hosted reactive database provider, with Convex as the current practical first test surface;
- self-hosted instance of the same/open-source backend class;
- data-sovereign colocated deployment where compute and evidence storage live inside the same infrastructure boundary, e.g. a Nebius-style deployment with real residency/certification controls.

## Hard invariant
Backend choice is a hosting/storage decision only. It must never change who can authorize, how a receipt is verified, or what the chokepoint accepts.

One authority chokepoint. Pluggable storage underneath it. Full stop.

## Sequencing
Do not build before the current chat/Kira/Fusion inside-out loop is reliable and the existing kernel capability-port waves are further along.

Suggested later sequence:
1. Extract current Convex/read-only surfaces into an adapter-shaped interface.
2. Prove the same receipt/evidence semantics across a local/file adapter and Convex adapter.
3. Add deployment-specific adapters only after test parity exists.

## Acceptance before implementation
- Adapter contract declares read/write semantics and exactly what data is persisted.
- Tests prove identical verification behavior across at least two adapters.
- Tests prove no adapter can grant authority, bypass AUMLOK, or alter receipt meaning.
- Secrets/envs/keys remain outside tracked source and outside receipts.
