## Body

Captured from third-party static architecture/red-team review of the latest GitHub snapshot. Verify against current code before implementation.

Concern:
Kira is advisory, but advisory memory poisoning matters because it influences reviews and future proposals. verifyBrainState should strongly bind atoms to receipts, not just chain shape/order.

Goal:
Make Kira state tamper-evident at atom/content level and write it atomically.

Required checks:
- recompute atom id from canonical atom content or a clearly documented canonical preimage
- verify atom.id matches receipt.atomId
- verify receipt inputHash equals canonical input fields
- verify atom fields match receipt kind/source/scope/tags/links
- no orphan receipts and no orphan atoms
- state writes use temp file + fsync + rename where possible

Acceptance tests:
- editing atom text without updating receipt fails verification
- editing receipt chain without atom match fails
- orphan atom/receipt fails
- interrupted write does not corrupt existing brain state

Non-goal:
Kira remains advisory. This does not grant memory authority over gates or applies.

## #79 — atomic writes landed (commit `d2bc5c1`); the atom↔receipt binding is scoped + findings below

Verified against current code (`core/src/kiraBrain.ts`) before touching anything. Split into a small safe win (landed) + a precise findings note for the riskier half (owner-present).

### Landed now — atomic writes (1 of the 6 required checks + 1 acceptance test)
`saveBrainState` wrote with a plain `fs.writeFileSync` — an interrupted write could leave a half-written, unloadable brain. It now writes to a temp file in the **same directory** (rename atomic on one filesystem), `fsync`s, then `rename`s over the target; a failing/interrupted write leaves the previous brain **byte-identical**, temp cleaned up on failure. Tests prove: success → no temp litter + reloads; failed write (unwritable dir) → original byte-identical + fully loadable + no litter. ✅ "interrupted write does not corrupt existing brain state".

### Deliberately NOT landed tonight — the atom/content binding (needs owner-present verification)
Current `verifyBrainState` (`kiraBrain.ts:427`) checks: chain shape/order (sequence + previousHash), receipt `id` self-consistency (`makeReceiptId`), receipt→atom existence, atom→receipt existence, authority flags, forbidden-content. **Gaps vs the issue's required checks:**

1. **Content not bound.** It never recomputes `receipt.inputHash` from the atom's content, so **editing `atom.text` without touching the receipt is NOT caught today** (the atom id derives from `inputHash`+sequence, not from text directly). Canonical preimage at ingest (`kiraBrain.ts:234`): `sha256(JSON.stringify({kind, text, source, scope, tags, links}))`. The atom stores all six fields, so a verify-time recompute-and-compare is possible.
2. **atom id not recomputed.** `makeAtomId(inputHash, sequence) = atom_${sequence}_${inputHash.slice(0,16)}` (`kiraBrain.ts:186`) — verify could recompute and compare `atom.id`.
3. **Pairing not cross-checked.** Only existence is verified, not that `receipt.atomId === atom.id` AND `atom.receiptId === receipt.id` as a matched pair.
4. **Atom fields vs receipt.** `kind/source/scope` are in `makeReceiptId`'s preimage; verify could assert the atom's fields match the receipt's.

**Why it's owner-gated, not a tonight change:** a strengthened verify that recomputes the canonical preimage will turn the **real persisted brain** (`state/kira/brain.json`, ~76 atoms) RED if the reconstruction isn't byte-identical to what ingest produced — especially default normalization for `source/scope/tags/links` and key order. `loadBrainState`/`saveBrainState` both call `verifyBrainState`, so a false-positive would brick the live brain and the anchor. That wants a run against the real brain with you present (recompute, confirm every existing atom still matches, THEN pin). Happy to build it as the next Kira round once you're around to watch the real-brain verify go green.
